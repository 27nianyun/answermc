## 组合工序配方摆放多样化（等价摆放放宽）

用户诉求：原本摆在右上角的配方可以挪到左下角等其他位置，只要合成结构没变也能合成。

- **先验证再动手**：写探测脚本全量遍历 446 个 grid-shaped 配方 × 全部平移位置（1228 个），发现**平移早已 100% 支持**（`trimIdx` 裁掉空行空列实现了平移等价），UI 层也无阻碍（9 格全可点）。所以问题不是「不支持平移」，而是等价范围太窄 + 玩家不知道可以自由摆。
- **等价规则最终定为三条**（`src/transforms.ts` 的 `checkPlacement`）：
  1. 任意平移（原有，`trimIdx` 实现）
  2. 左右镜像（原有，对所有配方安全）
  3. **180° 旋转（新增）**：`rotateHalf` + `trimGrid`，但仅对 `inputs.length >= 3` 的配方生效
- **两处刻意的限制（都有实测依据）**：
  - 不做 90°/270°：3×2 的门旋转 90° 会变成 2×3，那恰好是「活板门」的合法摆法，会让两个不同配方互相误判（实测冲突 120 例）。
  - 1~2 格不做 180°：像 `bundle`（string/leather 竖排）这种配方，「旋转 180°」与「上下颠倒材料」在几何上是同一件事，放宽就等于允许放错材料。修正前实测有 7 例误判（bundle/candle/end_rod/jack_o_lantern/lever/redstone_torch/sticky_piston），加限制后降为 **0**。
- **顺带修的隐患**：`trimIdx`/`trimGrid` 裁剪后各行长度可能不一致，导致后续旋转/比较时 `r is not iterable` 崩溃，已补齐行宽（补 `-1`/`null`）。
- **组合工序重构的教训**：中途尝试把两步链扩展成 2~4 步随机游走，但 `stick` 这类基础材料在 block/item 转化池里没有上游配方，导致链条生成率反而归零、3 条冒烟测试挂掉，已回退。**教训：放宽等价前必须先写反向测试（交换材料必须判错），否则「更宽容」很容易变成「判错」。**
- **UI 提示**：`.craft-grid-wrap` + `.craft-grid-hint`（工作台下方说明「任意位置/转半圈/镜像都行，只要相对结构没变」）；组合工序标题下新增 `.chain-lead` 同类说明。
- **新增 5 条常驻回归测试**（`smoke-transforms.ts`）：任意平移全通过（1228/1228）、左右镜像全通过（446/446）、3 格以上 180° 旋转通过（45/45）、交换两个不同材料一律判错（0 泄漏）、非方阵 90° 旋转判错。测试数 49 → 54。

## 燃料可互换（烧制类工序的燃料槽接受任意可燃物）

用户诉求：煤炭、木炭等具有相同作用的物品在烧制等工序中可以互相代替——木头、木板、木制工具也能当燃料。

### 关键发现：官方燃料表不在标签里，而在代码里
- 先误判为「jar 内没有燃料标签」→ 其实只是不在 `data/minecraft/tags/` 下。
- 真正的权威来源是 **`net/minecraft/world/level/block/entity/FuelValues.class`** 的 `vanillaBurnTimes()`：64 条 `add(ItemLike/TagKey, burnTime)` 注册 + 最后一步 `remove(#non_flammable_wood)`。
- 提取方法：jar 里已有 JDK（`/c/Program Files/Java/jdk-26.0.1/bin/javap.exe`，注意 `javap` 不在 PATH），`javap -p -c` 后按 `getstatic → Builder.add/remove` 的顺序扒出注册序列。展开标签后**共 280 项**。
- 顺带修正 `extract-jar.mjs`：26.1 起物品标签在 `data/minecraft/tags/item/`（此前只解压了 `tags/block/`），漏解压导致 `netherite_tool_materials` 等标签解析不到，转化数 1082 → 1096（多出 14 条 smith/smelt，是修复不是回归）。

### 两个真实的命名空间坑
1. `tags/block/` 与 `tags/item/` 存在**同名标签文件**（`logs`、`planks`、`signs`、`non_flammable_wood`…）。`tagRaw` 用 `set` 覆盖 → 必须让 **item 命名空间优先**（配方与 FuelValues 引用的都是 `ItemTags`），并给 `set` 前加 `if (tagRaw.has(tag)) continue`。
2. `non_flammable_wood` **只存在于 item 命名空间**（下界菌木）。若 item 侧缺失，`warped_planks`/`crimson_stem` 等 32 项会被误当燃料。

### 架构决策：燃料表存全局，不塞进 inputs
280 项若塞进 `transform.inputs[1].names` 会：① 撑爆材料盘；② 让组合工序生成「先烧出煤 → 再用煤当燃料烧 X」的假链条；③ JSON 重复 110 份。改为：
- `meta.fuels` 存**全局一份**燃料表；燃料槽改成 `{ names: [], tag: null, fuelSlot: true }` 标记。
- `checkPlacement` 的 furnace 分支改查 `isFuelName(slots[1])`（`FUEL_SET.has`）。
- 过滤条件 `inputs.every(names.length > 0)` 必须放行 fuelSlot（`hasCandidates`），否则 110 条 furnace 转化全部被踢出池子。
- `feedsInto` 与 `chainForResult` 遍历**必须跳过 fuelSlot**，否则组合工序把燃料当中间产物。
- furnace 的 `signature` 里燃料槽写 `*`，否则所有烧制撞成同一 signature 被去重（会只剩 70 条）。
- `expectedSlots` 燃料槽返回 `DEFAULT_FUEL`（charcoal）供提示/揭晓使用。

### 材料盘只展示 2/3/4 个代表燃料
`sampleFuels()` 按 8 个分组（煤/木板/原木/木制品/木制工具/木家具/竹草/特殊）各挑一个，保证类型有区分度。**并额外剔除「既是干扰项又是合法燃料」的项**——`charcoal`（原木→木炭）材料本身就是 36 种燃料原木，同家族捞到的木板/木台阶看着像干扰项，实际塞燃料槽也判对，会让玩家以为自己摆错了。全量扫描确认泄漏 0。

### 测试
`smoke-transforms.ts` 从 54 → **79 条**，新增：308→280 项燃料表校验、每条烧制 × 每种燃料全交叉（33880/33880 判对）、石头/铁锭/玻璃不算燃料、下界菌木不算燃料、材料燃料放反判错、盘面燃料 2/3/4 递增且都可用、无假链条。
- **写断言的教训**：不能直接用 `isFuelName` 计数判断"盘面展示了几个燃料"——`charcoal` 那条的材料本身就是 36 种燃料原木，会被误算成 40 个。要用 `isFuelName(n) && !material.has(n)`。

### 用户反馈
> 有"题目主角"不就相当于泄露答案了吗

**反馈完全正确。** 实测旧版 **232/347 道题（67%）的主角图标就是正确答案本身**，0 道安全。这直接违反本项目「未揭晓零泄漏」的核心原则。

### 改法
- `src/types.ts`：`subjectName: string | null` → `optionNames: (string | null)[]`（与 `options` 一一对应）。
- `scripts/generate-quiz.mjs`：`add()` 重构为接收 `choices` 配对数组（`choice(label, name, answer)` / `asChoices(答案, 答案名, 干扰项, 干扰项名)`），内部 shuffle 后同时产出 options / answerIndex / optionNames。15 个题型全部改写。
- `src/quiz.ts`：`subjectEntry()` → `optionEntries()` 返回与 options 一一对应的条目数组；新增 `optionsHaveUniformIcons()`。
- `src/components/QuizGame.tsx`：删掉整个 `.quiz-subject` JSX 区块；选项内按 `sprites[index]` 渲染该选项自己的图标。
- `src/App.css`：`.quiz-subject*` 全删，新增 `.quiz-option-sprite`（42px 格 + 12px 网格底）；答对/答错时图标边框跟着变色。

### 顺带挖出并修掉一个数据层大 bug：126 组译名撞车
零泄漏校验在生成期硬拦题干时，抓出一批涂蜡题的「答案」和「原料」是同一个方块（「给避雷针涂蜡 → 得到什么？」→ 避雷针）。追下去发现根因在 `generate-catalog.mjs`：

**zh.minecraft.wiki 的 Autolink 模块译名格式是 `通用名|变种全名`**：
```lua
[ "waxed copper bars" ] = '铜栏杆|涂蜡的铜栏杆'
[ "deepslate gold ore" ] = '金矿石|深层金矿石'
```
斜杠前是**通用名**（一大堆变种共用），斜杠后才是**专属全名**。而 `stripMarkup()` 里有 `.replace(/\|.*$/, '')` —— **把消歧信息直接丢掉了**。结果 126 组同类型内撞车（涂蜡态 / 氧化态 / 深板岩态 / 墙挂态 / 颜色变种全被抹平成同一个名字）。

修法：
1. `parseLuaName()` 拆出 `{ generic, specific }` 两段，`chineseFor(name, display, 'specific')` 可按需取。
2. 新增 `disambiguateZhNames(entries)`：只在**同一个 kind 内出现重名且注册名不同**时才消歧（避免把「石头既是方块也是物品」这种跨类型正常复用也改掉）；**谁手里有 specific 谁升级**，通用名留给没有专属全名的那条。
   - ⚠️ 不能按注册名字典序挑「基础条目」：`deepslate_gold_ore` 字典序排在 `gold_ore` 前面，那样会让有专属译名的深层矿反过来霸占「金矿石」，把真正的金矿石挤进重名里（这个坑踩过一次）。
3. `manualSpecificNames` 手工补 wiki 漏收的 2 条：`filled_map: '已填充的地图'`、`breeze_wind_charge: '旋风箭'`。
4. 顺手修 `netherStemNames` 里 `crimson_hyphae` 误写成「菌柄」，应为「绯红菌核」。

**结果：570 条升级，同类型内撞车组 126 → 0。** 副作用是好事：题库从 347 → 361 道（多出 14 道因译名区分开而能出的题）。

### 零泄漏守卫（`scripts/smoke-quiz.ts` 10 条断言）
数据层：optionNames 一一对应且可解析 / 图标一律全出或全不出（部分出会让玩家靠「哪个没图」反推）/ 题库无 subjectName 字段 / 题干不泄露答案。
UI 层：对 `QuizGame.tsx` 与 `App.css` 源码做正则守卫 —— 无 `quiz-subject`、无 `subjectEntry|subjectName`、图标不得写死 `[0]` 或 `[answerIndex]`、图标必须由 `sprites[index]` 循环下标驱动。
- ⚠️ **守卫匹配前必须先剥注释**（`stripComments`）：注释里要写「这里曾经有过题目主角」这段历史，否则守卫会被自己的说明文字触发（踩过：2 条误报）。
- ⚠️ 题干泄露检查要区分**真泄露**与**原料引用**：「把『绿宝石矿石』放进熔炉烧制，会得到什么？」答案是「绿宝石」，但原料是**已知输入**不是答案提示。判据：答案文本 < 3 字（句中疑问词）不算；或题干里存在**更长的注册名**包含该答案文本（说明在讲那个更长条目的原料）不算。
- ⚠️ 判据里的名字集合必须用**中文译名**（`entry.zhName`），不能用 `entryByName` 的键 —— 那是英文注册名，跟中文题干永远对不上（踩过：20 道误报）。

### 验证
`tsc -b` 0 error、`npx oxlint src scripts` 0 warning/0 error、`vite build --outDir dist-verify` ✓、`npm run smoke` **52 yesno + 79 transforms + 82 quiz = 213 条全过**。预览 http://localhost:4205/ （HTTP 200）。

### 教训
**零泄漏这类问题必须靠断言常态化，不能靠人眼。** 「题目主角」看起来是个很体贴的 UI 设计（给个图标帮助识别），但放在四选一里就是送答案。同理，任何「只显示一个对象」的 UI 在选择题里都要先问一句：这个对象会不会本身就是答案？

## 第五轮：难度切换 / 选项打乱 / 不重复 / 考试模式 / 题库扩到 476 道

用户需求五连：`加入切换不同难度的功能，同一道题每次选项打乱，也可以勾选不重复刷新一道题，还可以有考试模式，计时答题看分数，再加入更多的题目`

### 1. 难度切换（组件内三级按钮 + 与侧栏双向同步）
`src/components/QuizGame.tsx` 内加「入门 / 进阶 / 极限」三按钮，同时给 App 传回调让侧栏下拉跟着变。
- 组件内切：`switchLevel()` 调 `onDifficultyChange(next)` 同步回 App。
- 侧栏切：`useEffect(() => { setLevel(difficulty); setHistory([]); setRound(1) }, [difficulty])` 反向同步进组件。
- **教训**：两处难度入口必须双向同步，否则用户从侧栏改难度后答题区还按旧难度出题，且两边显示不一致。

### 2. 每次选项打乱（`shuffleQuestionOptions`）
```ts
const order = question.options.map((_, index) => index)
for (let index = order.length - 1; index > 0; index -= 1) { /* Fisher–Yates */ }
return { ...question,
  options: order.map((i) => question.options[i]),
  optionNames: order.map((i) => question.optionNames[i]),
  answerIndex: order.indexOf(question.answerIndex) }
```
- **关键约束**：`options` / `optionNames` / `answerIndex` 三个数组**必须用同一个 index 置换一起重排**。只重排 `options` 会让图标与文本错位（上一轮零泄漏修复引入的 `optionNames` 数组最容易被漏掉）。
- 用 Fisher–Yates 而不是 `sort(() => Math.random() - 0.5)`：后者不保证均匀，且比较器不严格时可能漏点。
- 顺序完全没变就返回原题，省一次对象分配。
- 实测 240 次打乱覆盖**全部 24 种排列**；2000 次模拟零错位。

### 3. 「不重复」勾选
`pickQuestion(pool, previousIds, seed, allowRepeat)` 加第四参；`allowRepeat` 为真时不排除已出过的题。勾选框默认 `true`。
- 实测：勾选时 200 轮零重复；取消勾选时 200 轮重复 62 次（证明勾选框真在起作用，不是摆设）。

### 4. 考试模式（`EXAM_PRESETS` 10/20/30 题 · 每题 30 秒 · 计分）
- **计分**：`basePoints(难度, 题)` × `timeFactor`，`timeFactor = 0.4 + 0.6 * clamp(secondsLeft / 30)` —— 答得越快分越高，但**保底 40%**，秒末答对也不至于和满血答对同分。obscure 题基础分更高（hardcore 240 / 其他 180）。
- **评级**：S–D 五档，按正确率 + 超时数综合。
- **超时**：用 `timeLeftRef` 存真实秒数，在 interval 回调里判归零后调 `commitExamAnswer(null)`。
- ⚠️ **不要在 `setState` updater 里做副作用**。原写法 `setTimeLeft(prev => { ...; commitExamAnswer(null) })` 是 React 反模式（updater 必须是纯函数，StrictMode 下会跑两次）。用 ref 存真值、回调里做副作用。
- ⚠️ `timeLeftRef` 声明顺序要在 `startExam` 之前，否则 TDZ 报错。

### ⚠️ 本轮修掉的真 bug：考试模式当场泄题
现象：`answered` 被写成 `status !== 'playing' || (isExam && running && picked !== null)`，考试点完答案后选项立刻染成 `right`/`wrong` 并显示对勾叉号 —— **等于当场把答案告诉玩家，后面的题随便猜**。

修法（拆成两个语义不同的变量）：
```tsx
const answered   = status !== 'playing'   // 练习模式：答完 / 揭晓
const examLocked = isExam && running && picked !== null  // 考试：只锁定，不判对错
const locked     = answered || examLocked // 只用于按钮禁用

const state = examLocked
  ? isPicked ? 'picked' : 'idle'
  : !answered ? (isOut ? 'out' : '') : isAnswer ? 'right' : isPicked ? 'wrong' : 'dim'
```
配套新增 `.quiz-option.picked` 样式（刻意**不给**对错反馈），并在 `smoke-quiz.ts` 加 3 条回归守卫：
- 考试锁定态用独立 `picked` 样式，不复用 `right/wrong`；
- 考试锁定时不渲染对勾 / 叉号；
- `answered` 不再包含考试锁定态（泄题根源的守卫）。

**教训：锁定态和已揭晓态在 UI 上必须是两个不同的状态机分支。** 只要「锁定」被并进「已揭晓」，就会顺带把正确答案的视觉反馈泄露出去。凡是「先不让知道对错」的场景（考试、闯关、盲猜）都要单独开一个只标「我选了哪个」的样式。

## 第四轮：题库认知难度重构（用户反馈「题目太简单了」）

### 问题定位
「简单」不是题量问题。分两轮找出的根因：

**第一轮 —— 数值题结构缺陷**
1. 干扰项从全池随机取：硬度题抽出过「水 / 淡蓝色床 / 石英砖 / 激活铁轨」找最高，闭眼剔掉「水」就赢了。
2. 全是极值题（「以下哪个最 X」）：答案天然是四个选项里最大/最小的，只要会排序就一定答对，不需要精确记忆任何数值。

**第二轮 —— 数值题修好后，level 1 里还剩 156 道正向语义题**（这才是「太简单」的残余）
- 34 道「要用哪类工具采掘」：看到石头就知道要镐。
- 30 道「哪个能当燃料」：看到煤就知道是燃料。
- 26 道「哪个是透明的」：看到玻璃就知道透明。
- 30 道烧制 + 20 道去皮 + 20 道涂蜡：干扰项从全池乱取，会混入根本不是该工序产物的选项。
- 10 道敌对生物分类：图鉴里 mob 只有 10 个（6 敌对 + 4 被动），一眼就能认出来。

### 对策：换结构，而不是继续调数值
- **双条件交叉题**：同时核对两行数据，三个干扰项各只满足其中一个条件，只查一行必被绊倒。
  - 工具 × 遮光等级 / 发光等级 / 可透光
  - 燃料 × 加工原料（必须同时查燃料表和配方表）
- **反向排除题**：问「哪一个【不】能…… / 不能…… / 不是……」，必须确认另外三个都满足。
  - 不能用斧头去皮、不能用蜂蜜瓶涂蜡、不是透明的、【不】需要用镐/斧头
- **精确目标值题批量生成**（题型 26）：六个字段各自出题，答案强制既非最大值也非最小值。
  - 字段：硬度、爆炸抗性、发光等级、遮光等级、堆叠上限、生物碰撞宽度
- 加工题干扰项改为**同一工序的其他产物**（如烧制题干扰项全部取自 smelt 结果集）。

### 新增/重构的难度工具（scripts/generate-quiz.mjs）
- `targetValueChoices({ target, pool, random, valueOf, requireMiddle, maxDistinct })`
  出「精确目标值题」。**关键实现是枚举三元组而不是取最近三个**：
  硬度、爆炸抗性的最近邻里大量同值（1.5 附近挤着一堆 1.4/1.5/1.8），直接取前三个会得到重复取值被 `add()` 静默丢弃。
  早期版本正是在这里栽了：能凑齐「四值互异 + 答案居中」的硬度档位只有 **2 个**，放宽 span 也救不回来；改成枚举回溯后同样的规则覆盖 **24 个档位**。

### 踩坑清单（本轮新增）
1. **perBucket 必须限流**。题型 26 最初不限量，遮光等级 0 这一档有 449 个方块、堆叠 64 有 2264 个 —— 透明题一家膨胀到 **588 道**，把「方块 / 光照」挤到只剩 66 道、爆炸只剩 2 道，题库结构失衡。现在加 `perBucket` + 桶 > 150 时额外限到 `bigBucket`。
2. **零泄漏自守会把反向题全部拦掉**。去皮反向题最初从「像木头」的模糊匹配里找答案，结果 49 个候选只捞出 3 个，且「去皮X」与「X」互为子串，触发泄露拦截，**题目一道都没出成**。改成从「木头家族」（木板/木台阶/木楼梯/木栅栏/木门…）里取才对 —— 这些同样由木头加工而来但不在去皮表里。
3. **mob 池只有 10 个，双条件交叉会重复**。试过「敌对/被动 × 体型档位」，10 道题里 4 道题干选项完全一样（恶魂/末影龙反复出现），毫无意义。改出「精确碰撞宽度题」，数值（0.35/0.49/0.52/0.7/0.9/1/1.4）彼此极近，必须查表。
4. **回溯枚举三元组的三重循环性能可接受**（24 个候选 → C(24,3) = 2024 组合，生成 700 道题无压力）。
5. `numericChoice` 仍需要 `keyOf` 参数（内部 `neighboursOf` 要用），只有 `targetValueChoices` 把它去掉了 —— 改签名时别把两个搞混。
6. `oxlint` 对未使用的函数参数报警（`(entry) =>` 但函数体没用 entry），改成 `() =>`。

## 第二轮：扩题 + 修旧题 + 流畅度 + 查 BUG

### 1. 修了 5 个真实 BUG（不是风格问题，是会崩 / 会算错的）
- **条件调用 Hook（会白屏崩溃）**：`QuizGame` 把 `useMemo(sprites)` 写在 `if (!question) return null` 之后 ——
  首帧题目为空不调用、下一帧突然调用，Hook 数量跳变，React 直接抛错。
  同类问题在 `CraftingGame` 的 `if (chain) {}` 分支里也有 4 处 useMemo，一并提到所有 early return 之前。
  **教训：给本项目写 Hook 时，`return null` / `return <JSX>` 之前不许出现任何 Hook。**
- **setState updater 里做副作用**：`commitExamAnswer` 原来在 `setExamAnswers` 的 updater 内调
  `setRunning` / `setExamResult`。改用 `examAnswersRef` 持有权威值，updater 之外做交卷判定。
- **考试分数两套口径**：侧栏 `persistStats` 写死 +60 分，成绩单用 `examPoints`（难度×时间系数），
  两边对不上。现在 `commitExamAnswer` 返回 record，`choose` 用 `record.points`。
- **勾「不重复」不重抽**：`setRound(1)` 在 round 已是 1 时不触发重渲染，effect 不跑。
  引入只增不减的 `drawSeq` + `bumpDraw()`。
- **提前交卷少算一题**：读 `examAnswers` state 会比 ref 少一条（刚答完那帧未提交），改读 ref。

### 2. 文案修订（34 道 → 0 道）

- 修选项长度悬殊：**34 道差 >14 字 → 0 道**。长解释搬进 explanation，选项只留结论。
  批量改写脚本 `scripts/patch-quiz-wording.mjs`（一次性，可重跑）。
- **新发现并修的守卫漏洞**：`allSentenceOptions` 判据只看长度和标点，把「32 种 / 硬度 1.5」

### 3. 扩题：721 → 824 道

新文件 `src/knowledge.ts`。答对一题点亮一个知识点维度，维度取 topic 第二段

### 踩坑：重建 dist 会让 vite preview 变成坏引用（用户报「点不了答案」）
现象：预览页整个应用加载不出来，界面上什么都点不了 —— **不是交互 bug，是白屏**。
根因链：`vite preview` 把 `index.html` 缓存在内存里 → 先 `vite build --outDir dist-verify`，
再单独 `vite build`（输出到 `dist`）→ vite build **清空输出目录**，`dist` 的旧 js 被删
→ 但 preview 服务还活着，返回的是**旧内存里的 index.html**，引用着已不存在的 js
→ 404 → 白屏 → 表现为「点不了」。

**最有力的证据**：坏引用的文件名（`index-BoCnXnZz.js`）在磁盘上根本不存在。
这类问题先跑这一条：curl 拿到 preview 返回的 js 文件名，和 `ls dist*/assets/` 对比，必须对得上。

修复：`taskkill //PID <pid> //F` 杀 preview 进程（4205 上常有 IPv4/IPv6 两个进程，两个都杀），
重新构建它服务的那个目录，再启动。

**以后验证流程固定为**：
1. `npx vite build --outDir dist-verify`
2. grep 出 `dist-verify/index.html` 引用的 js/css，逐个 curl 确认 200
3. **不要再单独 `vite build` 到 `dist`** —— 两个输出目录并存时，
   preview 指向哪个必须记清楚，否则就会出现「磁盘是新的、服务的还是旧的」

### 修「除了正确答案都不能选择」（真 bug，但代码是对的）
现象：答对一题后四个选项全部 `disabled` 且全灰，玩家以为界面坏了。
**代码逐行看完全正确** —— `disabled={locked || isOut}`，答对后锁死四项是正确的反作弊设计。
真问题在**视觉与文案没告诉玩家该点「继续」**，四个灰选项和「坏了」无法区分。

**三种验证手段全部失效过，这个教训很贵**：
1. 逻辑推演（复刻状态机）→ 结论「代码正确」，但没发现体验问题
2. `react-dom/server` 渲染 QuizGame → 得到 **0 个选项按钮**（首帧题目为空，
   useEffect 在 SSR 不跑），DOM 里根本没有 `.quiz-option` 可查，**这条路直接不通**
3. 读 CSS / grep disabled → 也都正常
最后靠 **CDP 连真实 Chrome 点一下**才看清：click 后 class 变成
`dim has-icon` × 3 + `right has-icon` × 1，disabled 全 true。

**三处修复**：
1. 反馈文案加 `ANSWERED_HINT`（「本题已结束，点『继续』出下一题。」）—— 直接指出路
2. `.quiz-option.dim` 透明度 0.5 → **0.62**：disabled 的灰和已揭晓的灰必须差一档，
   否则玩家分不清「不能点」和「已答完」
3. **加键盘答题**：A/B/C/D 或 1-4 选答案，Enter 揭晓 / 下一题。纯鼠标要来回移两次。

**键盘 effect 的三个坑（都踩了）**：
- Hook 必须写在 `if (!question) return null` **之前**。我第一版写在

### 根因：`.segmented` 横向基类在 CSS 里根本不存在
全项目只有 `.segmented.vertical`（侧栏那处）有样式，裸 `.segmented` 没有任何声明。

所以断言的是计算样式：display / 外框宽度 / **相邻按钮的实际像素间隙** / 按钮宽度 / active 唯一且有底色。
